# GoDo Spec: Local-First Sync

Status: draft · Last updated: 2026-10-25

## Summary

GoDo is a todo app with a CLI, a desktop app, and a web app. Todos are stored in a plain-text [todo.txt](https://github.com/todotxt/todo.txt) file on each device, and a sync server keeps devices in agreement. Users who don't want a local file can run in **online mode**, where every operation goes straight to the server.

## Goals

- Todos live in a plain-text file you can edit with any editor, and GoDo picks up those edits.
- Every write works offline in local mode and is never lost.
- Multiple devices converge on the same list without manual intervention.
- Users choose per device between local mode and online mode.
- One shared core package serves the CLI, desktop app, and server.

## Non-goals (for now)

- Real-time collaborative editing of a single todo.
- Shared lists between users.
- A native mobile app. Phones use the web app, installable as a PWA.
- CRDTs. Per-todo merging is enough for short, line-based items.

## Concepts

| Term            | Meaning                                                                               |
| --------------- | ------------------------------------------------------------------------------------- |
| **Local mode**  | The device reads and writes `todo.txt` and syncs in the background.                   |
| **Online mode** | The device has no local file and calls the `/todos` API for every operation.          |
| **ID**          | A stable, client-generated identifier (ULID) for each todo, stored as a todo.txt tag. |
| **Base**        | A snapshot of every todo as it was after the device's last successful sync.           |
| **seq**         | A per-user counter on the server. It goes up by one on every write.                   |
| **Tombstone**   | A server row marking a todo as deleted, so deletes propagate.                         |

## The todo.txt format

The only field required from the user is the text of the todo. Standard todo.txt syntax will be supported, with two tags added by GoDo: `id` and `mod` (time last modified):

```
(A) 2026-10-20 Call dentist +health @phone due:2026-11-01 id:01JB8Z3K4MQ7Y2R5T8V0WXCDEF mod:2026-10-25T14:02:11Z
x 2026-10-24 2026-10-20 Renew passport id:01JB8Z5QRTN3H6K9M2P4S7V0XA mod:2026-10-24T09:12:00Z
```

- `id:` is a ULID generated by the client that creates the todo. It never changes. Todos that existed before sync have a UUID instead (see the migration below). IDs are opaque strings, compared byte for byte and never case-normalized.
- `mod:` is a UTC timestamp, set whenever a GoDo client changes the todo. If the user edits a line in an editor, the sync engine notices the change and sets `mod:` itself.
- A line without an `id:` was added by hand. The sync engine assigns it an ID and a `mod:` and rewrites the line.
- Display commands hide `id:` and `mod:` by default.

**Archiving** follows the todo.txt convention: archived todos move from `todo.txt` to `done.txt`. The sync engine treats both files as one set, with `archived` derived from which file a line is in.

## Modes

Each device picks a mode in its config:

```toml
mode = "local"   # or "online"
todo_dir = "~/todo"
server = "https://godo.example.com"
```

Both modes implement the same interface (see [Store interface](#store-interface)). A user can mix modes across devices: writes from online-mode devices bump `seq` like any other write, so local-mode devices receive them on their next sync.

### Online mode tradeoffs

- Writes fail with a clear error when the server can't be reached.
- Concurrent edits are detected immediately. Clients send the todo's `version` in `If-Match`, and the server returns `409 Conflict` when it doesn't match. The client refetches and tells the user.
- There is no plain-text file. `godo export` writes a read-only snapshot of the server's todos to a file.
- `godo import <file>` does the reverse: it uploads an existing todo.txt file, for example when a todo.txt user signs up or switches a device from local to online mode.

## Local mode

### Writes

Every write is local only:

1. Parse `todo.txt` (and `done.txt` if needed).
2. Apply the change. A new todo gets a fresh `id:` and `mod:`. An updated todo gets an updated `mod:`.
3. Write the file atomically: write to a temp file, then rename over the original.
4. Sync. The CLI waits up to 2 seconds for it so it can report a failure (see [Status](#status)). The desktop app syncs in the background. A failed sync is never reported as a failed write.

### Sync state

Stored in the platform state directory (for example `~/.local/state/godo/`), never next to `todo.txt`:

```
sync.json      { "last_seq": 42, "last_synced_at": "2026-10-25T14:02:13Z" }
base.json      every todo as of the last successful sync, including archived ones:
               { "<id>": { "line": "...", "mod": "...", "archived": false, "version": 3 } }
```

`version` is the server version from the last sync. It's what the client sends as `base_version`, so it has to live in sync state, because the todo.txt line doesn't record it.

### Detecting local changes

Compare the current files with `base.json`, keyed by `id`:

| File vs. base            | Change sent to the server |
| ------------------------ | ------------------------- |
| ID in file, not in base  | create                    |
| ID in both, line differs | update                    |
| ID in base, not in file  | delete                    |
| Line has no ID           | assign an ID, then create |

The comparison is the outbox. If a sync fails, nothing is queued: the next sync compares again and finds the same changes.

### Sync cycle

1. Take a local file lock (`flock`) on the todo directory so that a CLI command and the desktop app don't sync at the same time.
2. Diff the files against base to collect local changes.
3. Send `POST /sync` with `since = last_seq` and the changes.
4. Write the server's response into the files. The server's version wins for every row it returns, because it has already resolved conflicts.
5. Save the new base and `last_seq`.
6. Release the lock.

If the user edits a todo in an editor while a sync is running, step 4 must not overwrite that edit. Before writing, re-read the file. For any ID whose line differs from the one sent in step 3, keep the local line and leave it for the next sync.

### When sync runs

- After every write, if online.
- On app start, on window focus (desktop and web), and every 60 seconds while the app is open.
- On demand with `godo sync`.

**Retries (desktop and web).** When a sync fails because the server can't be reached, the app retries with exponential backoff: wait 1s, then 2s, 4s, 8s, and so on, up to a 5-minute cap. Each wait gets ±20% random jitter. A successful sync resets the delay, and so does any event that suggests the network is back (window focus, an OS network-change event, a new local write). This avoids hammering the server or draining a battery while offline. The CLI doesn't retry. It makes one attempt per command, and the next command tries again.

### Status

Successful syncs are silent. Messages appear only when changes are stuck on this device:

```
$ godo add "Call dentist"
Added. Offline: 1 change not yet synced.
```

- The CLI reports a failure if the sync after a write fails or times out.
- `godo status` always reports, because the user asked: `✓ synced 2m ago`, or `⚠ 3 unsynced changes · last synced 2h ago`.
- The desktop and web apps show a small indicator, which turns into a warning only when there are unsynced changes and the last sync attempt failed.

## Sync protocol

### `POST /sync`

Requires authentication. Pushing and pulling happen in a single round trip.

Request:

```json
{
  "since": 41,
  "changes": [
    {
      "id": "01JB8Z3K4M",
      "line": "(A) Call dentist due:2026-11-01",
      "archived": false,
      "deleted": false,
      "mod": "2026-10-25T14:02:11Z",
      "base_version": 3
    }
  ]
}
```

- `line` is the todo.txt line without the `id:` and `mod:` tags. The server parses it to fill in priority, contexts, projects, and the other fields.
- `base_version` is the server `version` the client last saw for this todo, or `0` for a new todo.

Response:

```json
{
  "seq": 44,
  "changes": [
    {
      "id": "01JB8Z3K4M",
      "line": "...",
      "archived": false,
      "deleted": false,
      "mod": "...",
      "version": 4
    }
  ]
}
```

The response contains every row for this user with `seq > since`, including the rows just pushed, in their final, server-resolved form. Sending `since = 0` requests a full resync.

### Server algorithm

Run everything in one transaction:

1. Lock the user's row with `SELECT sync_seq FROM users WHERE id = $1 FOR UPDATE`. Postgres holds a row lock until the transaction commits or rolls back, and any other transaction that tries to lock or update the same row waits. So `/sync` and `/todos` writes for one user run one at a time, and their `seq` values commit in order. Writes for different users lock different rows and don't block each other.

   A global Postgres sequence would not be enough. Two transactions can take seq 7 and 8 and commit in the opposite order. A client that syncs between those commits sees 8, records `last_seq = 8`, and never receives 7.
2. For each change, take the next `seq` (`sync_seq + 1`, `+ 2`, …). At the end, write the final value back to `users.sync_seq`.
3. For each change:
   - No existing row: insert it.
   - `base_version` equals the row's `version`: apply the change.
   - Otherwise there's a conflict, resolved by [the merge rules](#merge-rules).
   - Every applied change sets `version = version + 1`, `updated_at = mod`, and `seq` to the new value.
4. Select and return all rows with `seq > since`.

### Merge rules

**v1: per-todo last writer wins.** On a conflict, the change with the later `mod` wins. The losing edit is discarded. If it's a delete that loses to an edit, the todo comes back.

**Later: field-level merge.** Treat done status, priority, text, due date, and archived as separate fields, and merge each one with a three-way comparison against base. With this, "marked done on the laptop" and "reprioritized on the phone" both survive. The change stays inside the merge function, and the protocol doesn't change.

**Clock skew.** `mod` comes from device clocks, so a device with a fast clock wins more conflicts than it should. That's acceptable for a personal todo list. Conflicts are only resolved by timestamp after versions have shown a real conflict, so skew never affects non-conflicting edits.

### Tombstones

Deletes are soft. A deleted row stays with `deleted_at` set so the delete can reach other devices. Tombstones older than 90 days may be pruned. A client whose `last_seq` is older than the pruning horizon receives `410 Gone` and does a full resync.

## Server changes

### Schema

Migration `000006_add_sync`:

```sql
ALTER TABLE users ADD COLUMN sync_seq bigint NOT NULL DEFAULT 0;

ALTER TABLE todos
  ADD COLUMN uid text,                 -- client ID; becomes the public ID
  ADD COLUMN updated_at timestamptz NOT NULL DEFAULT NOW(),
  ADD COLUMN deleted_at timestamptz,
  ADD COLUMN seq bigint NOT NULL DEFAULT 0;

UPDATE todos SET uid = gen_random_uuid()::text WHERE uid IS NULL;  -- existing rows get UUIDs
ALTER TABLE todos ALTER COLUMN uid SET NOT NULL;
CREATE UNIQUE INDEX todos_user_uid ON todos (user_id, uid);
CREATE INDEX todos_user_seq ON todos (user_id, seq);
```

The existing `version` column is used for conflict detection. `bigserial id` stays as an internal key, and APIs expose `uid`.

### Existing `/todos` endpoints

These keep working for online mode and the web app, with three changes:

- Write handlers bump the user's `sync_seq` and set the row's `seq`, using the same helper as `/sync`.
- `DELETE` writes a tombstone instead of deleting the row.
- `PATCH` and `DELETE` honor `If-Match: <version>` and return `409` on mismatch.

### Push notifications (optional, later)

`GET /events` (server-sent events) sends `{"seq": N}` whenever the user's `sync_seq` changes. Clients respond by syncing. This only shortens the delay before devices pick up a change. Correctness never depends on it.

## Store interface

```go
// internal/store
type Store interface {
    List(ctx context.Context, f Filter) ([]todo.Todo, error)
    Get(ctx context.Context, id string) (todo.Todo, error)
    Add(ctx context.Context, t todo.Todo) (todo.Todo, error)
    Update(ctx context.Context, t todo.Todo) (todo.Todo, error)
    Delete(ctx context.Context, id string) error
}
```

- `filestore.Store` reads and writes `todo.txt`/`done.txt`. It does no network I/O.
- `apistore.Store` calls `/todos`.

The CLI and the desktop app depend only on `Store`. The mode is chosen once, at startup. In local mode, the caller runs `sync.Engine.Sync` after a write, so the CLI can decide how long to wait and what to report.

`Dockerfile` and the compose files live at the repo root so that `docker compose up` works from a fresh checkout with no `-f` flags.

Notes:

- `internal/todo`, `internal/syncproto`, and `internal/merge` do no I/O, so they can be tested with plain table tests. The server never imports `internal/sync`.
- The web frontend is shared. On desktop, Wails exposes the Go `Store` as bindings, and the frontend calls them through `backend/wails.ts`. On the web, the same components call the HTTP API through `backend/http.ts`. The web app always runs in online mode. See [Web app](#web-app).

## Web app

The frontend in `web/` is a Vue 3 + TypeScript app built with Vite. The same build runs in the browser and, later, inside the Wails desktop app.

```
web/src components ──► Backend (TS interface, mirrors store.Store)
                          ├── http.ts  ──► /v1/todos            (web: always online mode)
                          └── wails.ts ──► Go bindings ──► Store (desktop: local or online mode)
```

- **Components depend only on `Backend`.** `main.ts` provides one with `provide(backendKey, createBackend())`, and components get it with `inject(backendKey)`. `createBackend` picks the adapter. Errors map to `NotFoundError`, `ConflictError`, and `UnavailableError`, which mirror the `store` package's errors.
- **Parsing stays in Go.** The frontend sends todo.txt text and displays the structured fields that the server or the bindings return. It never parses todo.txt itself. The TypeScript `Todo` type mirrors the JSON from `/v1/todos`. For the desktop adapter, `todo.Todo` needs JSON tags that produce the same shape.
- **One origin.** In production, the API serves the built frontend: `web/dist` is embedded in the binary with `go:embed` when built with `-tags embedweb`, which the `Dockerfile` does. Requests that match no API route fall through to the frontend handler, which serves the file if it exists and `index.html` otherwise, so client-side routes work. `/v1/` and `/debug/` paths still get the JSON 404. In development, the Vite dev server proxies `/v1` to the API. Either way the browser makes no cross-origin requests, so CORS isn't involved.
- **Builds without Node.** Without the `embedweb` tag, `web.Dist()` returns nil and the API serves no frontend, so `go build ./...` works on a checkout that has never run `npm`.
- **Freshness and conflicts** follow [online mode](#online-mode-tradeoffs): refetch on window focus and periodically (SSE later), send `If-Match` on writes, and on `409` refetch and tell the user.

Open decisions:

- **Auth in the browser.** Keep the bearer token from `/v1/tokens/authentication` (simple, but readable by any XSS if stored in `localStorage`), or have the same endpoint also set an HttpOnly, `SameSite=Strict` session cookie for the web app.
- **CORS** only matters if the frontend is ever served from a different origin. The current preflight response doesn't allow the `If-Match` header.

## Build order

Each step leaves a working app.

1. **`internal/todo`**: todo.txt parser and formatter, with round-trip tests.
2. **`Store` interface + `apistore`**: refactor the CLI onto it. Online mode now works through the new structure.
3. **Migration 000006**: soft deletes, `seq` bumping in `/todos`, `If-Match` support.
4. **`POST /sync`**: server transaction, with integration tests against real Postgres.
5. **`internal/sync` + `filestore`**: diffing, merging, state files, locking. Local mode works in the CLI.
6. **Status UX**: `godo status`, offline messages.
7. **Dev and deploy tooling**: `docker compose up` for a fresh checkout, and a one-command deploy.
8. **Web app**, then the **Wails desktop app** wrapping the same frontend.
9. **SSE** push, and **field-level merge**.

## Testing

- **Parser**: round-trip every todo.txt example from the spec (parse, then format, gives the same line).
- **Merge**: a table of base/local/remote combinations, including edit/edit, edit/delete, delete/delete, and create/create.
- **Sync engine**: run two in-memory clients against a real server in a test, interleave offline edits, sync both in different orders, and check that both files end up identical.
- **Server**: concurrent `/sync` requests for one user never produce duplicate or out-of-order `seq` values.

## Open questions

- **Database**: stay on Postgres or move to SQLite. The spec assumes Postgres, which is the current setup. Nothing in the sync design depends on that choice: SQLite serializes writes on its own, so the `sync_seq` row lock becomes unnecessary but harmless.
- Should `mod:` be hidden from the file and kept only in sync state? Hiding it keeps the file cleaner. Keeping it in the file makes the file the single source of truth.
- Keep a conflict log (`godo conflicts`) so that edits lost to last-writer-wins can be recovered?
